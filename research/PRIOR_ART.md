# Prior art and collision gate

Literature cutoff and access review: **2026-09-05**. Status: **conditional, near-KILL**, not established novelty. This is an adversarial research baseline, not a systematic-review completeness claim. [SOURCES.json](SOURCES.json) distinguishes directly accessed primary material, scout-reported primary review, and unverified reuse terms. Paper results below are attributed reports, not replications by this project. Comparisons and selection judgments are **[INFERENCE]** unless explicitly described as direct source observations.

## The boundary worth testing

The selected question is whether persistence-sensitive **joint schedule/crash exploration** can expose reproducible cross-process recovery failures in unmodified local Linux workflows substantially more efficiently than strong one-trace and composed schedule/crash baselines. The possible contribution is a product-aware reduction with a bounded preservation argument and a later restricted native capability. Neither has been established.

The initial executable reference artifact is only a **finite whole-record model/oracle and baselines**: fixed existing records, atomic whole-record writes, independent per-record persistence prefixes, honored record flush, volatile handoff, fail-stop, and declared recovery predicates. It is not a POSIX/ext4 model, SQLite tester, FUSE supervisor, native process scheduler, namespace model, mmap implementation, or proof of real-world prevalence. No raw scratch counts are literature evidence; canonical results belong with the executable artifact.

### Claims already occupied

- Visibility before durability and a surviving dependent effect after loss of its source: **PMRace and DURINN**.
- Joint concurrency, reads-from, persistency and recovery-observer exploration with DPOR: **PerSeVerE**.
- Application crash-state construction from a trace and semantic checking: **ALICE and Pathfinder**.
- Tracing descendants: **ALICE**; changing native multi-process schedules and replaying them: **RACEPRO**.
- Controlled loss of unsynchronized regular-file data: **LazyFS**.
- Graphs, dependency closure, complete-support memoization, antichain representation, ordinary DPOR, dependency-DAG project management and bounded engineering loops: established methods, not project novelty.

### Required semantic separation

Keep three relations distinct when testing these collisions:

1. **Execution/read-from:** what supplied a visible value or synchronization observation in a feasible execution.
2. **Persists-before under model M:** which updates storage requires to survive together/in order. This defines legal crash images.
3. **Recovery obligation under oracle O:** which survived/lost combination violates the application's promise after recovery.

If a consumer requires its source to survive, inserting that desired implication as a storage-order edge would incorrectly make the target failure illegal. Conversely, treating every dirty read as a semantic obligation invents failures in independent logging and rebuildable caches. Read provenance at a syscall boundary is not exact semantic taint through an opaque binary. Recovery observations can branch and are not generally monotone in the persisted set; pruning by one dynamic recovery read set is not automatically sound.

## The strong composition, not a straw opponent

**RACEPRO-style feasible schedule exploration × ALICE/Pathfinder-style legal crash exploration**, with independent schedule POR, persistence-ideal enumeration, LazyFS-style fault realization where supported, and the same semantic oracle, already composes the headline features. A PerSeVerE-like recovery-observer baseline is also mandatory in overlapping finite semantics.

A distinct contribution would have to merge product cases that the strong independent composition cannot safely merge, with equal bad-outcome coverage inside a declared bound and a meaningful search-cost separation. Identical fixture/model/oracle inputs, unique recovery-observation counts and all pruning costs are necessary. Fewer duplicate traversal visits or ignoring recovery-unobserved records is not by itself a new reduction. Calling a finite reimplementation “Pathfinder-like” is not running Pathfinder.

A practical prevention null must remain visible: serialization, durability-before-handoff, immutable derived epochs, one durably published manifest and recovery validation. [Linux fsync(2)](https://man7.org/linux/man-pages/man2/fsync.2.html) directly states that flushing file data does not necessarily persist its containing directory entry. If a cheap conventional protocol removes the real problem, that weakens significance even if a tester is useful.

## Adjacent systems that prevent scope escape

- [FERRITE](https://homes.cs.washington.edu/~arvind/papers/fsmodel.pdf) already studies filesystem crash models and litmuses; [CrashMonkey/ACE](https://www.cs.utexas.edu/~vijay/papers/osdi18-crashmonkey.pdf) and [SnapCC](http://www.wingtecher.com/themes/WingTecherResearch/assets/papers/paper_from_25/SnapCC_TOSEM25.pdf) explore filesystem-implementation crash behavior. Changing the target to filesystem correctness does not create an empty field.
- [TxFS](https://www.usenix.org/system/files/conference/atc18/atc18-hu.pdf), [TxOS](https://www.sigops.org/s/conferences/sosp/2009/papers/porter-sosp09.pdf) and [Valor](https://www.usenix.org/legacy/event/fast09/tech/full_papers/spillane/spillane.pdf) occupy transaction-based prevention, including broader OS/subprocess effects. Do not rescue a failed tester thesis as a transparent universal transaction runtime.
- [BuildFS](https://arxiv.org/html/2005.06881), [Rattle](https://arxiv.org/html/2007.12737) and [Nix](https://edolstra.github.io/pubs/phd-thesis.pdf) cover build dependency/order hazards, caching, isolation and immutable publication. A build-order bug or atomic epoch publisher is not automatically a crash/concurrency contribution.
- [SQLite atomic commit](https://sqlite.org/atomiccommit.html) and [WAL](https://sqlite.org/wal.html) define the database's own protection boundary. A sibling-file mismatch is not evidence that SQLite atomic commit failed. SQLite is a planned workload/composition surface, not implemented coverage of the initial model.
- [Linux FUSE I/O modes](https://docs.kernel.org/filesystems/fuse/fuse-io.html) directly explains cached reads, readahead, one-to-many write-through requests, and delayed writeback requests. **FUSE requests are not application syscalls.** The raw page was needed to recover the substantive text during this review. A future backend needs a separately justified syscall/request mapping and process/IPC supervisor; it cannot silently approximate mmap, direct I/O, namespace persistence or mount escapes.

## Independent challenge disposition

The initial state-systems scout recommended only a cheap conditional pilot. The independent crash challenge strengthened this to **conditional, near-KILL**: kill VBD novelty, kill generic joint DPOR novelty, require a product-aware preservation/reduction result and later restricted native capability. Its larger suggested litmus vocabulary is **planned research**, not coverage of the delivered whole-record reference artifact. The independent evidence challenge killed the rival claim-liveness mechanism as standard action-cache/support invalidation; that makes Durability Debt relatively preferable, not positively proven novel.

## Rerunning the literature gate

Perform this before promoting a model result to a contribution, before native implementation commitments, and again before publication:

1. Open every direct predecessor above at a versioned paper/artifact, record access date, version/commit, exact supporting section and license file. Follow official artifact links and inspect implementation limitations, not only abstracts. Never treat an API error or a wrong license filename as absence.
2. Revisit PerSeVerE p-snapshots/recovery observers/DPOR, Pathfinder concurrency limitations and grouping heuristic, PMRace taint/post-failure validation, DURINN VBD/interleavings, ALICE issue-order semantics, RACEPRO resource/IPC replay and LazyFS data-only fault scope. Record a proposed claim-to-predecessor mapping with one concrete attempted translation for each claimed difference.
3. Forward/backward citation search, including recent work, with at least `"concurrency" "crash consistency" "partial order reduction"`, `"visible but not durable"`, `"process" "filesystem" "crash testing"`, `"PerSeVerE"`, and `"Pathfinder" "concurrency"`. Search PM and filesystem literatures, not only exact project terminology. Log databases, date ranges, exclusions and failed accesses; an empty result is not novelty.
4. Attempt the strong composition on the same finite input contract; attempt semantic translation to PerSeVerE. Record whether claimed savings come from existing observer pruning, conventional POR, duplicate elimination or a genuinely different product equivalence. Native execution comparisons require matching supported operations, not unequal capabilities.
5. Demand a nominated safe seed trace and alternate feasible bad schedule with the same initial image and oracle; preserve independent-log, recovery-repair and durability-before-handoff controls. A one-trace miss supports only a schedule-coverage gap, not efficiency against the composition.
6. **Stop promotion** if an equivalent predecessor is found, if any claimed advantage is routine composition, or if supporting source access/model fidelity is unresolved. Record `collision`, `inconclusive` or `conditional residual`, never “novel because no match found.” Keep the negative result and reopen selection rather than renaming the project.
